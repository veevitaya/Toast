# Toast - Food Decision Making App

## Overview
Toast is a mobile application designed to simplify food discovery for individuals and groups through a Tinder-style interface. It offers personalized restaurant recommendations, synchronized group swiping, and a "Taste Profile" to enhance user experience. The project aims to be a leading platform for social food discovery, leveraging gamification and LINE integration to boost user engagement and streamline dining decisions.

## System Architecture
Toast features a modern full-stack architecture with a React, Vite, TailwindCSS, and Framer Motion frontend, using TanStack React Query for state management and wouter for routing. The backend is powered by Express.js with PostgreSQL and Drizzle ORM.

**UI/UX and Design System:**
The design adopts an Airbnb-inspired aesthetic with a #FFCC02 golden yellow brand color, warm cream background, and white cards with soft shadows. Typography uses Plus Jakarta Sans for headings and Inter for body text. Animations are spring-based for structural elements and CSS transitions for interactive components. Key UI elements include a draggable bottom sheet, animated emoji filters, horizontally scrollable restaurant rows, and a floating multi-session status bar. Interactive maps use Leaflet with custom styled divIcons. The admin panel features a semantic color system with distinct colors for different functional areas and a yellow accent for global elements. The owner portal uses a green accent.

**Key Features:**
- **Onboarding Flow:** Quick 2-step onboarding (name + cuisine preferences) gates first-time solo/group entry. Stored in `toast_user_profile` localStorage; syncs name to guest profiles. Onboarding page at `/onboarding?returnTo=...`.
- **Personalized Recommendations:** Home screen displays an interactive map and personalized recommendations. Solo Journey uses a 3-step quiz, and "Toast Decides" offers personalized picks based on user preferences, context, and a "Daily Craving Engine" with a "Refine my picks" bottom sheet for advanced filtering.
- **Group Decision Making:** Users can create group sessions, invite friends via LINE, and collectively decide on a restaurant through synchronized swiping with a waiting room and session summary. Waiting room identifies host (gold border + star + "Host" label) vs members (green + checkmark + "Ready") using server-side `hostLineUserId`.
- **Trending Feed:** A TikTok-style vertical feed featuring snap-scrolling restaurant cards, media carousels, and action buttons.
- **Taste Profile:** Tracks user swipe behavior to personalize recommendations and offers a "TasteDNA" panel with aggregate scoring signals.
- **Restaurant Details & Saving:** Comprehensive restaurant information, deep links to delivery services, and a "Save Bucket System" for organizing saved restaurants.
- **User Profile & Preferences:** Manages dietary restrictions, preferences, and LINE integration settings.
- **Vibe Tagging System:** Restaurants are categorized using 14 distinct vibe tags, with an auto-assignment logic.
- **Admin Panel:** A comprehensive data analytics platform with an extensive set of pages for managing restaurants, users, campaigns, and viewing detailed analytics (Decision Intelligence, Performance, AI Recommendations, Delivery Conversions, Customer Insights). Features an Admin RBAC system.
- **Restaurant Owner System:** Dedicated login and dashboard for owners to manage restaurant details, menus, promotions, and performance analytics. Includes a multi-step restaurant claiming process and a subscription-based payment system.
- **"Butters" Assistant:** A dual-mode floating AI assistant available for both admin (yellow accent, "Admin Assistant") and owner (green accent, "Growth Assistant") users, providing page-aware context suggestions and insights.
- **Campaign System:** Enables restaurant owners to create and manage promotional campaigns.
- **Analytics Tracking:** Client-side event tracking for user behavior analysis, batched for efficiency.
- **Legal Center:** Comprehensive legal section with 7 documents (Privacy Policy, Terms of Service, Restaurant Partner Terms, AI Transparency, Platform Liability & Food Safety, Cookie Policy, Acceptable Use Policy). Accessible from Profile settings row and consent links in onboarding. Routes: `/legal` (list), `/legal/:slug` (viewer). Content stored as markdown files in `client/src/legal/en/`. Config in `client/src/legal/config.ts`.
- **Internationalization (i18n):** Full Thai/English language support with locale detection and `t()` function for UI text, stored in `localStorage`.
- **Search Functionality:** Matches restaurant names, categories, and menu keywords.
- **Performance Optimizations:** Lazy loading, critical asset preloading, database indexing, optimized backend queries, server-side in-memory caching, and frontend route lazy-loading. Toast Decides uses bootstrap-first rendering (sessionStorage cached), idle-callback API enrichment, optimized Unsplash image sizing (hero=400 q=50, secondary=200 q=40), sendBeacon analytics with fetch fallback (keepalive), and shared server-side event processing for single/batch endpoints. Route transitions use CSS `animate-page-in` keyframe (0.18s ease-out) instead of framer-motion springs. Render-path elements (greeting, context line, hero logo, TasteDNA panel, InsightCards) use CSS animations; framer-motion reserved for interaction-triggered animations (drawer gestures, bottom sheets, button presses). InteractiveMap is lazy-loaded with React.lazy/Suspense. Server API responses include Cache-Control headers (suggestions: 5min, restaurant detail: 2min, list: 1min). Bootstrap and personalized endpoints use reduced event query limits (50/80) for faster DB response. RestaurantRow is memoized with React.memo.
- **Reliability & Hardening:** React ErrorBoundary wraps the entire app to prevent blank screens from unhandled errors. API requests use AbortController with 15s timeout; queries auto-retry network errors (2x with exponential backoff). LIFF initialization has 8s timeout protection to prevent hung boot states. Swipe interactions have ref-based double-submit prevention on both SwipeDeck and GroupSwipe cards. All `<img>` tags have `onError` fallback handlers via centralized `imageUtils.ts`. Image preloading is deduplicated (Set-based) using `new Image()` warmup. Server-side rate limiting (in-memory buckets) protects swipe and analytics endpoints. Unhandled promise rejections are caught and logged. Server response logging truncates large JSON bodies (>500 chars) and flags slow requests (>2s).
- **Scalability & Database Optimization:** Database indexes on all frequently-queried columns: `analytics_events(user_id, event_type, timestamp, restaurant_id)`, `group_session_members(session_code)`, `group_swipes(session_code, line_user_id, composite)`, `restaurants(owner_id, trending_score, google_place_id)`, `campaigns(restaurant_owner_key)`, `user_behavior_events(user_id)`, `user_preferences(user_id)`, `decision_sessions(user_id)`, `mood_choice_links(user_id)`. GIN index on `restaurants(vibes)` for array containment queries. Connection pool configured (max=20, idle=30s, connect=5s). Server-side in-memory cache with TTL (restaurants=30s, counts=60s) and auto-invalidation on mutations. All direct `fetch()` calls across 15+ client files replaced with `fetchWithTimeout` (15s AbortController). GroupSwipe and WaitingRoom polling use abort controllers that clean up on component unmount. N+1 queries eliminated: `seedRestaurants` uses batch insert (50/batch), `getGroupMatches` uses SQL `GROUP BY HAVING` instead of in-memory map, `finalizeSessionStats` bulk-loads restaurant map once instead of per-match `getRestaurantById`, admin claims endpoint pre-loads owners+restaurants with `Promise.all`.
- **Security Hardening:** Helmet middleware provides CSP (Content-Security-Policy compatible with LINE LIFF), HSTS, X-Content-Type-Options, X-Frame-Options, and other security headers. Payload size limits (1MB) on express.json/urlencoded. Request ID generation (crypto.randomBytes) on every request for traceability. Rate limiting on admin/owner login (5/min per IP), session creation (10/min per IP), profile reads (30/10s per IP), claim submissions (5/min per IP), campaign updates (10/min per IP), taste DNA reads (20/10s per IP), personalized recommendations (30/10s per IP), and user stats (20/10s per IP). Rate limit buckets capped at 10,000 entries with emergency eviction to prevent memory exhaustion under attack. Login audit logging for both admin and owner authentication (success/failure with IP). Audit log table (`audit_logs`) tracks sensitive admin/owner actions (login, claim approval/rejection, restaurant deletion, restaurant updates, campaign deletion). Session event log table (`session_events`) records all critical group session lifecycle events. Group session codes are server-generated using `crypto.randomBytes` (8-char hex). Health endpoint (`/api/health`) reports uptime, memory, and latency metrics. **Phase 4 hardening:** All campaign endpoints require `ownerAuth` or `adminAuth`; campaign ownership enforced server-side (IDOR prevention). All PATCH endpoints use field whitelisting. Group session endpoints sanitize member responses (strip lat/lng), enforce membership checks, and validate state transitions (waiting→swiping→completed only). Sessions expire after 24 hours. Profile GET strips `partnerLineUserId`. **Phase 4b hardening:** Auth middleware (`adminAuth`/`ownerAuth`) now verifies password hash on every request — previously only checked username/email existence (critical auth bypass fixed). Client tokens include password in Base64 payload (`_k` field in session storage). Subscription tier enforcement via `requireTier()` — campaign creation requires `growth` tier or above. TIER_HIERARCHY: free(0) < growth(1) < premium/pro(2) < enterprise(3). Cross-user data isolation: user-stats endpoint requires `requesterId` matching `userId` (prevents enumeration). Personalized and taste-dna endpoints rate-limited to prevent cross-user probing.

**Technical Implementations:**
- **Personalization & Recommendation Engine (`server/recommendation/`):** Multi-layer transparent recommendation system powering Toast Decides. Architecture: (1) **Taste DNA** — long-term preference profile with 10 scalar scores (comfort, exploration, healthy, indulgent, spicy, distance, budget, novelty, speed) plus cuisine affinity/dislike maps; (2) **Moment Engine** — context-aware scoring using daypart, mood, area, weather, weekend; (3) **Candidate Generation** — fast shortlisting (max 50) by daypart, area, price, avoidance; (4) **Ranking Engine** — weighted multi-component scoring: 35% long_term_fit + 30% context_fit + 15% recency_novelty_fit + 15% market_quality_fit + 5% exploration_bonus - penalties; (5) **Confidence Model** — separate from score, computed from margin, data completeness, context clarity, consistency; (6) **Explanation Engine** — reason chips generated from actual score contributors, never fake. Event weighting with decay logic (exp(-days/decay_constant)), learning rates (+0.02 strong, +0.01 medium, +0.005 weak, -0.015 repeated negative). New tables: `taste_context_patterns` (contextual cuisine patterns), `recent_meal_memory` (repetition reduction), `user_behavior_events` (structured event log), `mood_choice_links` (mood-to-cuisine learning). Background Taste DNA worker updates incrementally on each relevant event.
- **LINE LIFF Integration:** Deep integration for user authentication, profile retrieval, and social sharing, including server-side token verification and group session invites with mandatory LINE permission flow.
- **Real-time Group Sessions:** Backend-powered sessions using PostgreSQL tables for `group_sessions`, `group_session_members`, and `group_swipes`, supporting trending sessions with geolocation-based restaurant fetching. Group sessions now track a `memberFingerprint` (sorted member IDs) to identify unique group combinations across sessions. Per-user stats (`user_swipe_stats`) and per-combo stats (`group_combo_stats`) are computed when viewing results, enabling historical trends — total matches, favorite cuisines, and session counts for both individuals and specific group combinations. The Top Picks page shows this session's stats, combo history (if same group has played before), and each member's all-time likes/dislikes/trends. **Group session bug fixes:** (1) Match/result data is now server-driven — the `/matches` and `/swipes` endpoints return full restaurant objects so all users see identical matched restaurants regardless of their local card order; (2) Stats bar shows aggregate "Total Swipes" + "Group Likes" instead of individual stats; (3) Back button in RestaurantDetail checks `sessionStorage("group_results_return")` for proper group results navigation; (4) Session completion screen with "Session complete — time to eat!" banner, "Wrap it up" host button, "Order {top pick}" CTA, and "Back to swiping" link when mid-session.
- **Data Model:** Structured PostgreSQL tables for all core entities.
- **Session Management:** Utilizes `sessionStorage` with `useSyncExternalStore` for persistent, global session tracking.
- **Google Places API Integration:** Backend supports fetching and importing restaurant data from Google Places API, with auto-deduplication, auto-vibe assignment, and auto-district detection.
