# Toast - Food Decision Making App

## Overview
Toast is a Tinder-style food discovery mobile application designed to help users decide what to eat, both individually and with friends. The project aims to provide a fun, interactive, and personalized experience for finding restaurants, incorporating features like a solo quiz for recommendations, synchronized group swiping, and a personalized "Taste Profile." The business vision is to become a leading platform for social food discovery, leveraging gamification and LINE integration to drive user engagement and facilitate dining decisions.

## System Architecture
The application features a modern full-stack architecture. The frontend is built with React, Vite, TailwindCSS, and Framer Motion for a dynamic and visually appealing user interface. State management is handled by TanStack React Query, and routing uses wouter. The backend leverages Express.js with PostgreSQL and Drizzle ORM for robust data management.

**UI/UX and Design System:**
The design adheres to an Airbnb-inspired system with a #FFCC02 golden yellow brand color, warm cream background, and pure white cards with soft layered shadows. Typography uses Plus Jakarta Sans for headings and Inter for body text. Animations are spring-based for structural elements (drawers, modals, page transitions) using Framer Motion, while interactive elements use CSS transitions. Key UI components include a draggable bottom sheet, animated emoji filters, horizontally scrollable restaurant rows, and a floating multi-session status bar. The interactive map uses Leaflet with custom divIcons for markers, styled with a warm illustrated CSS filter.

Each restaurant receives a 0-99 match score. Endpoint: POST `/api/restaurants/personalized` accepts `{ userId, tasteProfile, hour, dayOfWeek }`. **Technical Implementations:**
- **LINE LIFF Integration:** Deep integration using the @line/liff SDK (LIFF ID: `2009293021-mFgkOhqd`, Channel ID: `2009293021`). Initializes on app load, provides user authentication, profile retrieval (userId, displayName, pictureUrl), and LINE shareTargetPicker for group invites. Guest fallback generates local profile for non-LINE users. LIFF URL: `https://liff.line.me/2009293021-mFgkOhqd`. The `VITE_LIFF_ID` env var controls LIFF initialization. **LINE OA Integration:** Separate LINE Official Account (Channel ID: `2009335625`, LIFF ID: `2009335625-Pyd3rjhr`, LIFF URL: `https://liff.line.me/2009335625-Pyd3rjhr`) for group invites — extracts user data (displayName, pictureUrl, userId) from LINE and auto-syncs to server via `POST /api/line/profile`. Env vars: `VITE_LINE_OA_LIFF_ID`, `VITE_LINE_OA_CHANNEL_ID`. Group invite links use LINE OA LIFF URL when available.
- **Real-time Group Sessions:** Backend-powered group sessions with PostgreSQL tables (`group_sessions`, `group_session_members`, `group_swipes`). Session flow: create session with code → invite friends via LINE share → friends join via `/group/waiting?session=CODE` → waiting room polls `/api/group/sessions/:code` every 2s for real member list → start swiping → each swipe recorded to API → matches computed server-side when all members swipe right on same item. **Trending Swipe Sessions:** The Swipe button on the Trending Feed creates a `sessionType="trending"` group session, opens LINE invite picker (non-redirect `shareMessageNoRedirect`), then navigates to the waiting room. WaitingRoom collects user geolocation and sends to server (POST `/api/group/sessions/:code/location`). When session starts, GroupSwipe loads trending restaurants via GET `/api/group/sessions/:code/trending-restaurants` which calculates the midpoint between all members' locations and fetches nearby restaurants from Google Places API (fallback: DB restaurants sorted by trending score + distance). Schema additions: `sessionType` and `sourceData` on `group_sessions`, `latitude` and `longitude` on `group_session_members`.
- **Data Model:** Structured PostgreSQL tables for `restaurants`, `user_preferences`, `user_profiles`, `campaigns`, `analytics_events`, `ad_banners`, `admin_users`, `restaurant_owners`, `restaurant_claims`, `group_sessions`, `group_session_members`, `group_swipes`.
- **Admin RBAC:** Admin users have roles (superadmin/admin/moderator/viewer) and granular permissions (manage_restaurants, manage_users, manage_campaigns, manage_banners, view_analytics, manage_claims, manage_config). Auth via `x-admin-token` header (base64-encoded username), validated server-side against DB. Session stored in localStorage as `toast_admin_session`.
- **Restaurant Owner System:** Dual login (admin vs restaurant owner) at `/admin/login`. Owner auth via `x-owner-token` header (base64-encoded email). Mock owner seeded on startup: email `owner@toastbkk.com`, password `owner2024`, linked to Jay Fai restaurant, verified, premium plan. Owner sidebar has 4 groups (Overview, Management, Insights, Account) with 7 nav items. Green #00B14F accent for owner sidebar. Owner dashboard at `/admin/my-restaurant` shows rich restaurant hero card (image, name, address, district, rating, price level, vibes, trending badge, verification/tier badges), engagement stats (views, likes, saves, delivery taps with trend indicators), quick actions grid (promotions, analytics, menu, reviews), owner profile card, performance highlights (engagement rate, unique visitors, trending score), active campaigns, claim system, subscription details. Sub-pages: `/admin/owner/menu` (operating hours, menu items CRUD, vibes), `/admin/owner/reviews` (review list, reply, stats), `/admin/owner/promotions` (campaign management), `/admin/owner/performance` (charts, peak hours, traffic sources), `/admin/owner/notifications`, `/admin/owner/settings` (profile/notifications/subscription tabs). Claims endpoint requires owner auth — ownerId derived server-side from session. Restaurant claims flow: owner submits claim → admin reviews in Claims Queue → approve/reject.
- **Session Management:** Utilizes `sessionStorage` with `useSyncExternalStore` for persistent, global session tracking across multiple concurrent sessions.
- **Search Functionality:** Matches restaurant names, categories, and menu keywords with priority.
- **Performance Optimizations:** Lazy loading for images and map iframes, and preloading of critical assets like the Toast logo.
