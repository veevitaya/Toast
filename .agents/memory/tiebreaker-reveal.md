# Tie-breaker reveal (fry race / duel → destination)

The resolved tie-breaker games render a full-screen stage (`absolute inset-0 z-[60]`) that runs its own timed sequence, then hands off to the shared `DestinationReveal` (dark "sealed" cloche: sealed→lifting→reveal→payoff). The fry race (`FryView`) was intentionally re-skinned to a LIGHT cream stage to match the requested old design — golden "THE REVEAL" eyebrow, dark "Longest fry wins" heading, realistic potato-style fries on a shared baseline (the climbing bars reuse `FryBody`'s look via a `RaceFry` helper — browned crispy tip, salt flecks, 3D side face, per-fry tone/lean/seed from the actual pulled fry; NOT flat gold bars), and a meta row (cm + cream letter-avatar + name) under each fry, with a crown dropping on the winner. The winner's solo-climb throb (`tbf-winnerThrob`) pulses a `filter` drop-shadow (the wrapper is transparent — a box-shadow throb would be invisible). **Do NOT revert it to the old dark `#070B16` stage.** There is a known light→dark cut at the handoff into the still-dark `DestinationReveal`; that's accepted (out of scope) — if it ever bothers, restyle DestinationReveal to cream rather than re-darkening the fry reveal. The `darkHold` loader is also cream to avoid a flash before the reveal mounts.

**Honesty guard (never fabricate a winner).** A resolved reveal must only crown a winner whose REAL data is present — `tb.winnerLineUserId` set, that id is in `participants`, and their pulled item exists (e.g. the fry `carton.find(picks[winnerId])`). If the resolved payload hasn't fully arrived, hold on the dark loader and let the poll fill it in.
**Why:** matches Toast's app-wide honesty principle (no fake fallbacks); a transient lagged/partial poll payload otherwise crowns a bogus winner — defaulting to `participants[0]` or flooring a length to `lenToCm(0)` = 7cm — for a split second.
**How to apply:** any resolved/settled reveal branch in `FryView`/`DuelView` — guard before rendering the celebratory reveal; render the dark loader otherwise.

**Poll-safe timers.** These reveals mount under a parent that re-renders on the ~1.5s tie-breaker poll. A timed/animation sequence must survive parent re-renders without restarting or double-firing:
- Stabilize parent callbacks (e.g. `onDone`) through a ref (`onDoneRef.current = onDone`) and guard the one-time handoff with a `doneRef` boolean, so the handoff effect can depend only on `[phase]`.
- Key the rAF/animation effect on primitive deps only (e.g. `[phase, maxCm]` where `maxCm` is a number) so re-renders with equal values don't re-run it; `setState` ticks inside the loop won't interrupt it.
**Why:** if an effect depends on a freshly-created callback identity or a recomputed object, every poll re-render cancels/restarts the animation or re-fires the handoff.

**DestinationReveal confetti = upward CANNON blast + top-down staggered rain (both, not either).** The reveal celebration is two independent particle groups: a one-shot confetti-cannon blast that fires UP and inward from the two bottom corners, arcs to an apex, then falls past the floor (`tbd-confettiCannon`, `forwards`; per-flake CSS vars `--x1`/`--x2` horizontal, `--peak` apex, `--drop` fall; outer span anchored `bottom-0 left-0`/`right-0`, `i%2` splits the two cannons; per-keyframe `animation-timing-function`s decelerate to the apex then accelerate down to fake gravity) layered in front of the continuous staggered rain falling from the top (`tbd-confettiFall`, infinite, slightly delayed so the blast reads first).
**Why:** user iterated through a pure top-down rain ("explode from the middle"), then a center radial explosion ("don't like the explode version"), and finally asked for it to "blast up naturally like a realistic confetti celebration" → the corner-cannon arc is that final ask. The replaced center-pop keyframe was `tbd-confettiBurst` (radial angle/velocity + `--g` gravity sag, anchored `left-1/2 top-1/2`); don't resurrect it. Don't collapse the two groups into one effect.
**Capture gotcha:** the cannon is one-shot `forwards`, so a screenshot of `?reveal=restaurant|menu` must be taken PROMPTLY (within ~1–2s of load) or the blast has already faded and only the rain shows. `tbd-burst` (medallion flash ring) is a DIFFERENT feature — leave it alone.

**The swipe-MATCH confetti (different component) now shares this cannon too.** `ConfettiExplosion` is defined separately in `GroupSwipe.tsx` (group swipe) and `SwipePage.tsx` (solo swipe) and fires on every match — this is the confetti users actually see in normal use, far more than the rare tie-breaker reveal. It used to be its own radial center-explode (`confetti-explode`/`confetti-fall` keyframes + `--tx`/`--ty`/`--ty-end`/`--spin` vars, anchored `top:40% left:50%`). It was converted to reuse the SAME global `tbd-confettiCannon` + `tbd-confettiTumble` keyframes (two-span flake), and the old keyframes/vars were deleted as dead.
**Why:** user kept asking to "apply this to the main app" after the tie-breaker cannon — the gap was that the visible everyday confetti (swipe match) was a separate old effect, NOT the tie-breaker reveal (which already had it). Lesson: when a user insists a change "isn't in the main app" after you've confirmed it is, look for a SECOND implementation of the same visual that they're actually seeing.
**How to apply:** the two `ConfettiExplosion` copies are duplicated (40→60 group / 120 solo pieces); keep them in sync if editing. They can't be screenshotted from a URL (need a real match) — verify via the shared keyframe already proven in the fry-reveal preview + clean compile.
**Realism mechanism (each flake is TWO nested spans, not one).** Outer wrapper animates only the motion PATH (burst arc-with-gravity, or flutter-fall that sways left↔right via `--sway` while descending slowly ~3–5s); inner flake runs `tbd-confettiTumble` — a continuous 3D `rotateX/rotateY` flip under `perspective` so it goes edge-on and shimmers like tumbling paper. Flakes are thin RECTANGLES (height ≈ 1.3–2.7× width, ~18% round foil dots), not dots. **Why:** a single-layer dot flying in a straight line "doesn't look like real confetti" (explicit user feedback); separating path from 3D-tumble is what sells it. Don't flatten back to one span / Z-only rotation / uniform circles.
**Confetti VISIBLE duration = the `reveal`→`payoff` phase gap, NOT the animation length.** The confetti only shows while `phase==='reveal'`; the `payoff` `DestinationScreen` is an opaque full-screen `bg-white z-[60]` card (confetti is z-40) that fades in and completely HIDES the confetti even though the fall rain is `infinite`. So "make the confetti last longer" = push the `setPhase('payoff')` timer later (it parked ~1.2s after reveal, felt too short; ~3.25s still felt too short → widened to ~6s), not change keyframe durations. The phase timer runs ONCE on mount and parks on payoff (waits for host's Lock-it-in).

**Fry-race scale must ZOOM to the contestants' band, not an absolute ruler.** Picked fry lengths cluster by luck (server `trueLen∈[0.28,1.0]`→9.5–16cm; players pull blind, often landing e.g. 10.1/10.3/10.4cm). On a fixed 0–16cm ruler those bars sit at ~63–65% — visually identical, so the requested "all rise together, longest keeps climbing while shorter ones freeze at different lengths" beat is invisible. Map heights through a dynamic window `floorCm=minCm-0.5*span, ceilCm=maxCm+0.7*span` (span floored ~0.4cm), and start the shared rising tape at `floorCm` (not 0). This yields a consistent staircase (~23–34% shortest → ~64–68% winner) for clustered, wide, and 2-player fields alike.
**Why:** the drama the user wants depends on visible per-fry gaps; absolute cm scaling erases them whenever the draw is tight (which is common).
**How to apply:** keep it HONEST — heights stay proportional to length *within the zoom*; each fry's real cm counts up (`Math.min(lvl,cm)`) in the meta row beneath it and freezes at its true length; show NO absolute numbered ruler (it'd lie about the zoomed scale). The cream reskin dropped the gridlines/tip-cm-tag entirely — cm lives in the meta row now.
